50 人课堂并发控制 review（2026-09-08）

本文保留修复前的审查基线；后续改动与复测见[并发修复验收](classroom-concurrency-fixes-20260908.md)。

结论：当前保存和报告事务能保护学生记录，但默认部署还不能通过“50 人同时进入、自由选参数做实验”的容量验收。本轮确认 2 个 P1 可用性问题、2 个 P2 并发边界问题。没有修改业务实现。

审查基于提交 `27db4ffb55307276ddd8f82f42bd256cb9ee725d`，实际数据 release 为 `2de76298d79646509efe0dfb49d8065d`（2016–2020）。使用本机独立 PostgreSQL 数据库和测试进程，50 个独立学生账号；原始表只读压力阶段复用一个账号，其余课堂阶段使用独立账号。Python 3.13.15、Uvicorn 0.49.0、12 个逻辑 CPU，沿用生产模板的 1 worker、64 连接/任务、256 backlog、16 个普通线程、4 个计算任务、8 个数据库连接以及数值库 2 线程配置。

[完整结构化证据](classroom-concurrency-review-20260908-evidence.json)保留测试口径、结果及排除样本；[本地复现脚本与截图](../dogfood-output/concurrency-review-20260908/)位于项目已有的忽略输出目录。Nginx 实测使用单 worker、本机 HTTP，保留模板的上游 keepalive 和代理超时；没有模拟生产 TLS、HTTP/2 或校园网络。

**1. [P1] 入口 64 连接限制与 50 人页面初始化的请求数量不匹配。**

位置：[生产启动参数](../deploy/gvcsim-api.service#L15)、[页面初始化](../frontend/src/App.tsx#L174)、[学生会话加载](../frontend/src/use-session.ts#L270)、[初始化失败页面](../frontend/src/App.tsx#L248)。

每名学生登录并校验身份后，并行请求 `meta`、`steps` 和 `classroom/session`，50 人可同时产生约 150 个请求。Uvicorn 的限制统计连接或请求任务，空闲 keepalive 连接也会消耗容量；超过限制立即返回 503，`backlog=256` 不会把这些已拒绝的 HTTP 请求排队重试。这与 [Uvicorn 官方对两种限制的说明](https://uvicorn.dev/server-behavior/)及本地安装版本的协议实现一致。

真实 Nginx → Uvicorn 测试逐人执行“登录 → me → 三个初始化请求”，不同阶段之间没有人为同步屏障。清空计算工作并重启进程后：50 人登录及 me 均成功，但三类初始化接口分别有 27、29、31 个 503，仅 18/50 人完成全部初始化。另一个直接面向 Uvicorn 的同步突发测试中，150 个请求全部为 503。后者是明确的同步突发上界，不代表每次课堂都会全部失败。

`meta` 或 `steps` 的一次 503 会把前端置为 `fatal`；这个页面只有错误文字，没有应用内重试入口，必须刷新。Nginx 的 `keepalive 64` 又与 API 的总连接阈值相同，不能据此认为“64 足够容纳 50 名学生”。独立 socket 探针还验证了：63 个空闲连接存在时，新来的 `/health/live` 也返回 503。

建议把传输连接预算与实际业务任务准入分开设计，按每名学生的请求展开量、Nginx worker 数及空闲连接预算一起确定配置，并保留轻量请求余量。初始化 GET 应提供恢复入口，可采用有限次数、带随机延迟的退避重试。增加 backlog 不会修复本问题，单独增大 worker 数也会改变所有进程内保护的总量。

**2. [P1] 原始表全局锁占满普通线程，使正常浏览超时，并拖慢登录和保存。**

位置：[原始表缓存与读锁](../gvcsim/data/icio_browser.py#L98)、[持锁读取 CSV](../gvcsim/data/icio_browser.py#L114)、[同步浏览路由](../gvcsim/data_routes.py#L117)、[同池执行认证](../gvcsim/api.py#L154)、[前端 10 秒期限](../frontend/src/api.ts#L68)。

`_read_columns()` 在一个进程级 `RLock` 内执行完整 CSV 扫描；不同国家、列集之间也互斥。50 名学生分头选择不同国家时，并非一个可由缓存合并的请求。同步路由先占用 AnyIO 普通线程，再等待这把锁，最多 16 个普通线程会一起被读表或等待锁占据。这里没有经过高成本任务的 4 并发限制，而认证与会话处理同样依赖这 16 个线程。

在干净进程中读取 2018 年 Z 表的 50 个不同列国家：服务端最终全部返回 200，但 p95 为 15.00 秒，17/50 个请求超过前端 10 秒期限。压力发生时，探针看到普通线程占用 `16/16`，另有 33 个任务等待；计算任务占用及等待均为 0。使用独立 HTTP 客户端插入的两个会话读取分别耗时 9.37 秒和 7.38 秒，排除了压测客户端连接池造成的假排队。

登录和保存会共享这条拥塞路径；本轮直接测量的是会话读取延迟。另在先前“未完成置换任务 + 原始表浏览”的混合阶段，agent-browser 实际观察到[登录 10 秒超时](../dogfood-output/concurrency-review-20260908/classroom-review-browser.png)，截图不作为上述干净进程数据的来源。

建议在进入普通线程前，异步等待原始表读取的独立有限配额；合并相同读取，并为认证、保存保留容量。缩短全局锁覆盖范围，避免无关列集共享长时间的读取锁。32 项列集缓存也小于本次 50 种工作集，需要用实际选国/切换年份/翻页轨迹检验反复淘汰的代价，而不只验证相同参数的热缓存。

**3. [P2] 只限制正在运行的计算，没有限制待计算队列；无人等待的工作仍会执行。**

位置：[CPU 配额](../gvcsim/concurrency.py#L12)、[创建在途任务与 shield](../gvcsim/singleflight.py#L40)、[仅对完成结果做 LRU 淘汰](../gvcsim/singleflight.py#L55)、[置换路由](../gvcsim/regression_routes.py#L375)。

`CapacityLimiter(4)` 约束同时执行的计算，`maxsize=64` 约束完成后的缓存，两者都不约束 `_inflight` 的数量和等待时间。`asyncio.shield()` 正确地保护了仍有其他学生等待的共享工作，但目前没有等待者计数：全部等待者都离开后，尚未开始的任务也留在队列中。

确定性调度探针提交 200 个不同键，先占住 4 个工作线程，再取消全部等待者：`inflight` 仍为 200，释放线程后最终执行了全部 200 项，完成缓存才缩至 64 项。该探针绕过 HTTP 检验内部边界，不声称 200 个 HTTP 请求能同时穿过 Uvicorn。实际场景可以通过学生超时、换参数、再次运行逐批累积工作；按账号每分钟限流不等于全局队列上限。

另以 50 个账号各提交一次 `n_draws=40`、不同 `seed` 的合法置换请求，22 个在 130 秒内成功，28 个仍超时。浏览器和 Nginx 的 mutation/read 期限只有 120 秒。这里刻意用 API seed 制造不同工作，原界面固定 seed；默认相同参数的另一个测试为 50/50 成功、4.65 秒内返回，监测确认只计算一次。因此问题发生在不同计算积压时，不应据此否定同参数合并的作用。

建议增加独立计算数量及等待期限限制、按学生的在途限制和适当公平性；对可预期超过请求期限的工作提供明确任务状态。共享任务仍有等待者时继续运行；最后一名等待者退出后应撤销尚未开始的工作。对已经运行的线程需单独设计协作取消或进程隔离，不能把停止等待当作终止 CPU 工作；[AnyIO 官方文档](https://anyio.readthedocs.io/en/stable/threads.html)也明确说明取消等待不会终止线程。相同键的重试现在会复用原任务，换键或报告重生成则没有这项保护。

**4. [P2] 首位学生的限流错误会传播给其他未超限学生。**

位置：[主回归限流位于共享 factory 内](../gvcsim/regression_routes.py#L334)、[置换的相同结构](../gvcsim/regression_routes.py#L375)。

共享键是 `release + operation + request parameters`，不包含账号，这是计算结果共享所需的行为。但配额校验在共享 factory 中使用首位请求者的 `account_id`。若该学生刚用完额度，他产生的 429 会成为所有加入该任务者的结果，即使其他人的额度尚未使用。

直接调用真实回归路由进行确定性复现：预先耗尽首位学生默认的 12 次额度，再让 50 个不同账号同时请求同一冷参数，50 个全部得到 429，其中 49 个账号没有使用过额度。未执行数值替身或数据读取，异常发生在限流处；该结果是路由调度证据，不是网络环境中的发生概率。

建议在把新的计算任务发布给其他等待者之前完成发起者准入检查，使拒绝只影响该请求。已有结果及已有计算仍可共享；避免直接把账号放入计算缓存键，否则会失去全班共享计算的收益。

**课堂阶段推演与实际测量**

| 阶段 | 请求/资源如何展开 | 本轮结果 |
| --- | --- | --- |
| 50 人首次登录 | 50 次密码校验；同一出口受 120 次/分钟来源限制 | 50/50 成功，直接 HTTP p95 0.204 秒 |
| 登录后进入课程 | 每人并行加载 3 个初始化接口 | 经 Nginx 仅 18/50 人全部成功，见问题 1 |
| 第 1 步分头看不同国家 | 不同列集扫描共享原始 CSV，锁和普通线程成为瓶颈 | 50 个最终 200，17 个晚于浏览器期限 |
| 课堂记录自动保存 | 每标签页 800ms 防抖、单个在途保存；数据库按账号及 release 更新 | 50 次小会话保存全部成功，p95 0.341 秒；50 份完整会话 p95 0.455 秒 |
| 每人同时打开两个标签页保存 | 同一 `base_updated_at` 竞争数据库条件更新 | 50 对请求均恰好一个 200、一个 409；该阶段客户端最多 50 个连接，单独检验一致性 |
| 全班运行同一个主回归 | 共享在途任务/缓存，等待请求仍占 HTTP 容量 | 50/50 成功，p95 0.562 秒，响应内容一致 |
| 全班运行同一个实体置换 | 50 个等待者共享 1 次计算 | 50/50 成功，p95 4.645 秒，计数探针确认计算 1 次 |
| 各自形成不同计算 | 最多 4 项执行，其余无期限等待 | API 不同 seed 压力下 28/50 超过 130 秒，见问题 3 |
| 50 人同时生成报告 | 每人独立构建，受计算配额约束；写入前再次检查会话版本 | 50 份草稿成功，p95 0.689 秒 |
| 50 人提交/重复提交 | 按各自报告行锁串行更新状态 | 两轮均 50/50 成功；第二轮 50 个版本戳均不变 |
| 教师查看全班报告 | 一次列表查询获得已提交报告 | 返回 50 份，约 0.111 秒 |

本轮报告使用完整课程夹具，其中四项默认回归均为可写入报告的 `invalid_design` 诊断；上述报告时延不代表所有可推断结果的时延。最终数据库核验为 50 名学生、50 份当前 release 会话、50 份待评报告，50 份报告均包含各自账号的显示名。

**已经成立的并发保护与剩余验收范围**

[会话条件更新](../gvcsim/classroom/records.py#L79)在 PostgreSQL 中原子检查版本；[报告落库](../gvcsim/classroom/records.py#L129)把会话行锁、版本检查和报告 upsert 放在一个事务；[重复提交](../gvcsim/classroom/records.py#L149)不会反复刷新版本。教师评分也有版本条件，重生成会清除旧评分。这些机制在本轮针对性测试中没有发现静默覆盖问题。4 项 CPU 配额先于普通线程取得，单就这类任务而言不会因排队占满普通线程；问题 2 来自未走这条路径的原始表读取。

后端相关测试 65 项通过，前端相关测试 40 项通过，生产前端构建通过。现有 [classroom 并发测试](../tests/test_classroom_concurrency.py#L51)只有 7 个不同任务及少量重复项，并没有覆盖 50 个真实 TCP 客户端、原始表不同列集或全部等待者离开；[部署容量测试](../tests/test_deploy_capacity.py#L7)验证配置文本包含 64，并不证明 64 适合课堂。

优先处理入口容量和原始表读取对普通线程的占用，再补队列生命周期及共享限流边界。修复后的放行应在目标机器上覆盖：50 人自然登录流程、不同国家/年份的冷读与反复切换、计算期间同时保存和教师查看、计算超时换参数、50 人课末提交。记录每阶段状态码、p95/p99、队列长度、线程占用与内存，并保持数据库版本冲突保护。当前结果证明可复现的问题和通过的具体场景，不构成任意硬件或更大班级的 SLA。

复现时请新建独立数据库，将 `GVCSIM_PG_DSN` 指向该库后运行 `classroom-init`；本轮脚本中的演示账号、固定端口及临时路径只适用于这个隔离环境。后端测试的 `teaching_db` 夹具会删除所连接数据库的 `public` schema，禁止把它指向已有课堂库。测试结束已停止本轮浏览器、Nginx 和 API 进程，删除本轮创建的数据库；保留报告、证据及复现输出。
